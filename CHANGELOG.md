# Изменения

## 1.0.0

### Поведение

- Обязательность полей и настройки значений по умолчанию берутся из описания схемы BPMSoft; `nullable` отделено от необходимости передать поле. Перед созданием возвращается список известных отсутствующих обязательных полей.

- Поля и типы разрешаются по метаданным, включая русские подписи и реальные lookup-навигации. Неоднозначные подписи требуют выбора.
- Чтение возвращает готовые display-карточки с русскими подписями, названиями связанных записей и датами.
- Добавлены `bpm_aggregate_records` и `bpm_find_duplicates`: серверные расчёты и группировка кандидатов с явной полнотой ограниченной выборки.
- Поиск и запись разрешают справочные значения на сервере. Приблизительные совпадения возвращаются кандидатами до изменения; переданные UUID проверяются.
- Несовместимый `tolower` в чтении и подсчёте имеет ограниченный fallback на коллацию платформы с предупреждением и временным кэшем проверенной совместимости по коллекции и сессии. Ошибки прав, таймауты и посторонние ошибки фильтра не маскируются.
- Пагинация v3/v4 соблюдает лимиты и сохраняет непоказанные записи, включая последнюю страницу и страницы с skiptoken. Подписанные cursors связаны с подключением и сессией.
- Кэши пользовательских данных разделены по полному контексту авторизации. Неизвестная полнота справочника не выдаётся за полный список.
- Изменения и запускающий процесс GET после сетевой неопределённости не повторяются автоматически. `outcome_unknown` содержит `safe_to_retry=false`.
- Создание принимает `idempotency_key`: известный UUID позволяет проверить результат и восстановиться после потери ответа.
- Предварительный просмотр и одноразовые `confirmation_token` связывают подтверждение с конкретными записями и данными операции.
- Пакетные результаты сопоставляются по ID; пропущенные, неизвестные и частично выполненные операции сохраняются в ответе.
- Сценарии проверяют переданные связи и владельцев до записи; при частичном выполнении возвращают выполненные шаги и известные UUID.
- HTTP-файловые инструменты ограничены выделенным `BPMSOFT_FILE_ROOT`, проверяют реальные пути и не перезаписывают существующие файлы. Локальный stdio сохраняет прежние пути.
- Двоичные поля используют маршруты по типу метаданных: `Edm.Stream` и `Edm.Binary` различаются. Пустой поток с ответом 204 возвращается как пустые байты, сохраняя проверку содержимого и безопасное продолжение загрузки.
- `.env` загружается при запуске; версия MCP берётся из `package.json`. Проверяются URL, числовые настройки, транспорт и Host/Origin. Добавлен `/healthz`.

### Миграция клиентов

- Минимальная версия Node.js — 22.
- stdio требует `BPMSOFT_ALLOW_ENV_CREDS=true`; сессия браузера не передаётся через stdio.
- Для HTTP-загрузок через `file_path` заранее помещайте файлы в `BPMSOFT_FILE_ROOT` (по умолчанию `./files`); сохранение также ограничено этим каталогом. Передача через `content_base64` / `return_base64` сохраняется.
- Внешний HTTP bind требует `MCP_ALLOWED_HOSTS`; общие env-креды разрешены только для loopback HTTP.
- Для защищённых изменений и удалений сначала получите предварительный просмотр, затем повторите те же параметры с `confirm=true` и `confirmation_token`. Массовое обновление больше не выполняется только по `expected_count`.
- `expected_etag` отклоняется, если платформа не предоставляет ETag. При поддержке версии конфликт возвращается как `concurrency_conflict`.
- Не предполагайте, что один приблизительный кандидат справочника уже выбран. Используйте точное значение или проверенный UUID.
- Сохраняйте `idempotency_key` и известный UUID на повтор создающей операции; новый ключ означает новое намерение.
- После перезапуска, смены авторизационного контекста или другого экземпляра процесса требуется новый cursor или план подтверждения.

Условные записи, уникальность бизнес-объектов между пользователями и транзакции нескольких шагов зависят от возможностей BPMSoft; эта версия не имитирует отсутствующие гарантии платформы.
