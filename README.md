# MCP-сервер для BPMSoft

Сервер связывает MCP-клиент с BPMSoft: находит записи, разрешает справочные значения, проверяет данные, создаёт и изменяет записи, выполняет готовые сценарии. Модель передаёт намерение и параметры; типы полей, OData-синтаксис, ссылки на справочники, пагинацию и контроль выполнения обрабатывает сервер.

Русские подписи полей доступны из метаданных конкретного инстанса. При неоднозначном поле или справочном значении сервер возвращает варианты до записи. Похожие названия служат подсказками: единственное приблизительное совпадение не становится автоматически выбранным UUID.

## Запуск

Нужны **Node.js 22+**, доступный BPMSoft и пользователь с необходимыми правами OData.

```bash
npm ci
npm run build
cp .env.example .env
# Укажите BPMSOFT_URL в локальном .env.
npm start
```

Сервер загружает `.env` из текущей рабочей папки; уже заданные переменные окружения имеют приоритет. Реальные адреса и секреты остаются в локальной конфигурации и исключены из Git. Версия в ответе MCP совпадает с `package.json`.

По умолчанию сервер принимает Streamable HTTP на `http://127.0.0.1:8007/mcp`. Также допустим путь `/`. `GET /healthz` возвращает состояние процесса и версию; он не проверяет доступность BPMSoft. Другие пути возвращают `404`, неподдерживаемые методы MCP — `405`.

### Несколько стендов: явное включение

Режим одного стенда сохраняется по умолчанию: используются `BPMSOFT_URL`, `/mcp` и `/`. Даже заданный `BPMSOFT_TENANTS_FILE` не переключает режим без `BPMSOFT_MULTITENANT=true`.

Для нескольких стендов оператор копирует [пример реестра](examples/tenants.example.json) в локальный `state/tenants.local.json` (каталог `state/` исключён из Git), задаёт свои адреса и включает режим в локальном `.env` явно:

```dotenv
BPMSOFT_MULTITENANT=true
BPMSOFT_TENANTS_FILE=./state/tenants.local.json
```

Формат: [examples/tenants.example.json](examples/tenants.example.json). Клиент подключается к `/tenants/<id>/mcp`; `id` выбирается только из файла оператора. URL и учётные данные из MCP-запроса не становятся настройкой подключения. У каждого стенда отдельный контейнер сервисов и разрешённый upstream origin. `/mcp` и `/` в этом режиме не выбирают стенд.

Мультитенантный режим поддерживает только HTTP с пользовательскими `BPMCSRF` и cookies, несовместим с общими env-кредами и `bpm_init`. `BPMSOFT_URL` в нём не определяет целевой стенд. Пример настроек клиента: [examples/http_multitenant_client_config.json](examples/http_multitenant_client_config.json). Реестр читается при запуске; изменение файла применяется после перезапуска.

## Авторизация и подключение

### HTTP: отдельная сессия каждого пользователя

MCP-клиент или интеграционный reverse proxy должен передавать актуальные `BPMCSRF` и `Cookie` при каждом HTTP-запросе. Сервер извлекает сессионные cookies, привязывает их к асинхронному контексту запроса и отправляет в BPMSoft вместе с `ForceUseSession: true`.

Сам MCP-сервер не получает сессию из браузера автоматически. Это обязанность клиента или адаптера авторизации. Наличие URL в настройках клиента не обеспечивает передачу cookies. Статичные токены истекают; подключение должно обновлять сессию пользователя.

Пример для клиентов, поддерживающих конфигурацию `type: "http"`:

```json
{
  "mcpServers": {
    "bpmsoft": {
      "type": "http",
      "url": "https://mcp.example.ru/mcp"
    }
  }
}
```

Названия полей настройки зависят от клиента. Пример соединения не содержит авторизации: её добавляет клиент или reverse proxy из текущей пользовательской сессии.

Сервер проверяет `Host` и браузерный `Origin`. Для loopback разрешены локальные адреса с портом сервера. Для `MCP_HTTP_HOST=0.0.0.0` или другого внешнего интерфейса обязателен `MCP_ALLOWED_HOSTS` — точные значения заголовка `Host`, включая порт, если он используется. `MCP_ALLOWED_ORIGINS` позволяет задать браузерные origins явно. Публикуйте HTTP-сервер через HTTPS reverse proxy и ограничьте прямой доступ к порту.

### stdio: локальное подключение одной учётной записи

stdio не передаёт HTTP-заголовки и browser cookies. Для локального процесса включите `BPMSOFT_ALLOW_ENV_CREDS=true` и задайте отдельного пользователя. Эти значения хранятся только в вашей локальной конфигурации.

```json
{
  "mcpServers": {
    "bpmsoft": {
      "command": "node",
      "args": ["/absolute/path/mcpBPMSoft/build/index.js"],
      "env": {
        "BPMSOFT_URL": "https://bpm.example.ru",
        "MCP_TRANSPORT": "stdio",
        "BPMSOFT_ALLOW_ENV_CREDS": "true",
        "BPMSOFT_USERNAME": "api-user",
        "BPMSOFT_PASSWORD": "REPLACE_IN_LOCAL_CONFIG"
      }
    }
  }
}
```

Рабочий шаблон: [examples/claude_desktop_config.json](examples/claude_desktop_config.json). В этом режиме доступен `bpm_init`; сервер выполняет login и обновляет истёкшую сессию. Одновременные запросы разделяют одну процедуру авторизации. HTTP с общими env-кредами допускается только при loopback bind; для удалённых пользователей требуется авторизация каждого запроса.

## Примеры использования

### Поиск по русским полям и справочникам

```json
{
  "collection": "Contact",
  "criteria": [
    { "field": "Город", "op": "равно", "value": "Москва" },
    { "field": "Дата создания", "op": "за последние N дней", "value": 30 }
  ],
  "top": 20
}
```

Вызов `bpm_search_records` разрешает поле и город, проверяет типы и формирует фильтр. Если в справочнике несколько городов с одинаковым названием, результат содержит варианты выбора. Передача UUID также допускается после проверки ссылки.

Сервер учитывает несовместимые функции поиска конкретной платформы. Если BPMSoft отклоняет приведение регистра или обрывает такой ответ, сервер повторяет только чтение с исходным полем, проверяет успешный результат и сообщает о сравнении по коллации BPMSoft. Проверенная совместимость кратковременно запоминается отдельно для коллекции и пользовательской сессии; подсчёт использует тот же механизм.

Для продолжения списка передайте `cursor` из предыдущего ответа в тот же инструмент. Сервер сохраняет параметры запроса и ограничивает выдачу. `count` означает число возвращённых записей, `total_count`, когда доступен, — число по фильтру; `has_more` указывает на продолжение. Подписанный cursor связан с подключением и пользовательской сессией, действует 30 минут. Перезапуск процесса делает старые cursors недействительными.

Полный JSON-результат инструмента с `readOnlyHint=true` ограничен **64 КиБ (65 536 байт UTF-8)**, включая `content`, `structuredContent` и метаданные. При превышении сервер возвращает `isError=true`, `code=response_too_large`, `response_bytes` и `response_limit_bytes`; данные и cursor отклонённого результата не возвращаются. Сузьте фильтр, перечислите поля в `select` и уменьшите `top`; при `auto_paginate=true` уменьшите `max_records` или отключите автопагинацию. Для количества используйте `bpm_count_records`, для показателей — инструменты агрегации с учётом их `complete` и `scanned_count`.

Это предел одного результата инструмента, без оболочки JSON-RPC, а не бюджет всей истории агента. Отдельно сохраняются прежние ограничения: 25 000 символов текста и 512 КиБ исходных записей списка. Результаты записи, файловые инструменты с `readOnlyHint=false` и MCP-ресурсы в этот предел не входят.

Помимо размера результата, каждый инструмент с `readOnlyHint=true` получает общий бюджет выполнения: **120 секунд, 100 фактических upstream запросов и 64 МиБ прочитанных декодированных данных**. Повторные попытки, перенаправления и параллельные чтения расходуют тот же бюджет. Его превышение возвращает `budget_exceeded`; сервер отменяет незавершённое чтение. Настройки: `BPMSOFT_READ_BUDGET_TIMEOUT`, `BPMSOFT_READ_BUDGET_REQUESTS`, `BPMSOFT_READ_BUDGET_BYTES`. Эти значения не заменяют лимит результата 64 КиБ и не распространяются на отдельно зарегистрированные MCP-ресурсы или инструменты с `readOnlyHint=false`.

HTTP допускает по умолчанию до 500 активных запросов, ещё 500 ожидающих и до 50 активных на один полный контекст пользовательской сессии и стенда. Переполненная очередь возвращает HTTP `429` с `Retry-After: 1`; запрос ещё не принят к выполнению. Лимиты задаются `MCP_MAX_CONCURRENT_REQUESTS`, `MCP_MAX_QUEUED_REQUESTS`, `MCP_MAX_CONCURRENT_PER_SCOPE`. Отключение клиента отменяет upstream ожидание; оно не отменяет уже выполненное изменение в BPMSoft.

### Дополнительные готовые инструменты

Сохранены возможности актуальной версии проекта: `bpm_whoami` (пользователь и время), `bpm_my_agenda`, `bpm_record_card`, `bpm_get_relations`, `bpm_aggregate`, `bpm_check_duplicates` и `bpm_merge_duplicates`. Строки заказов и счетов дополняются и пересчитываются сервером. Файловые инструменты сохраняют передачу содержимого через base64.

`bpm_find_duplicates` без `fields` выполняет профильный поиск по email, телефонам, ИНН и названию. Явный `fields` включает группировку по нормализованному совместному ключу с `complete` и `scanned_count`.

### Создание с защитой от повторного выполнения

Перед первым созданием в коллекции вызовите `bpm_get_schema`. Ответ содержит `required_fields` и `caller_required_fields`, подписи, типы и `default_hint`. Обязательность берётся из настоящего описания схемы BPMSoft; `nullable` — отдельное свойство. Автоматический UUID и поля с известным серверным значением по умолчанию не нужно заполнять вручную. Если часть описания недоступна, сервер явно отмечает неполноту вместо догадки.

Создание проверяет известные обязательные поля до отправки данных. Ошибка содержит `missing_fields` с названиями и подписями. Дополнительные условные правила BPMSoft могут проверяться только самой платформой; их ошибки также возвращаются агенту.

```json
{
  "collection": "Contact",
  "data": { "Name": "Пример Контакта", "Email": "contact@example.ru" },
  "idempotency_key": "contact-registration-unique-request"
}
```

Для `bpm_create_record` сохраняйте один ключ на одно намерение. Ключ определяет UUID в пределах подключения и пользователя. Повтор с тем же ключом и теми же данными возвращает уже созданную запись; другие данные дают `idempotency_conflict`. Не используйте новый ключ для простого повтора после потери ответа.

Механизм `idempotency_key` проверяет фактически сохранённые значения. Изменённая или удалённая после создания запись, смена сессии и платформенные бизнес-правила могут потребовать ручной проверки. Не считайте этот механизм распределённой транзакцией или бессрочной защитой от дублей. Готовые сценарии создания также принимают `idempotency_key`.

### Проверка потерянного ответа по журналу

Для одного стенда дисковый журнал включается явно через `BPMSOFT_JOURNAL_ROOT`. В мультитенантном режиме он включён с каталогом `./state/operations`, если оператор не задаёт другой путь. Каталог должен сохраняться при перезапуске и быть доступен только пользователю процесса.

Журнал сохраняет намерение до отправки изменения и исходы отдельных upstream этапов. Ответ содержит `operation_id` в тексте и `_meta`. Инструмент `bpm_get_operation` возвращает только операции текущего подтверждённого пользователя на выбранном стенде. Если ID потерян, вызовите его без `operation_id`: список постраничный, по умолчанию 20 операций, максимум 50; продолжение — `next_offset`. Порядок каталога не гарантирует сортировку по времени или неизменный снимок. Этапы одной операции также выдаются страницами через `stage_offset` и `stage_limit`.

Журнал помогает установить известный исход, но не повторяет изменение и не обеспечивает exactly-once. `outcome_unknown` или `requires_state_verification=true` требуют проверки BPMSoft перед новым действием; `safe_to_retry=false` нельзя трактовать как разрешение на автоматический повтор. Cookies и бинарные данные исключаются из штатных записей журнала, бизнес-данные намерения и ответа могут сохраняться.

В сценариях `created`, `contact_created` и `account_created` равны `true` после успешного создания, `false` при использовании уже существующей записи и `null`, если запись проверена после ошибки, но сам факт её создания этим вызовом неизвестен. Ответ сохраняет UUID и пояснение для продолжения.

### Массовое изменение с предварительным просмотром

Сначала вызовите `bpm_update_by_filter` с `criteria` (или готовым `filter`), данными и `expected_count`. Ответ содержит конкретные записи и `confirmation_token`. Покажите пользователю результат, затем повторите тот же вызов с `confirm: true` и полученным токеном.

```json
{
  "collection": "Activity",
  "criteria": [{ "field": "Дата создания", "op": "меньше", "value": "2025-01-01T00:00:00Z" }],
  "data": { "Status": "Завершена" },
  "expected_count": 12,
  "confirm": true,
  "confirmation_token": "TOKEN_FROM_PREVIEW"
}
```

Токен связан с подключением, пользователем и составом операции; действует 10 минут и используется один раз. Изменившийся набор записей или версия записи требует нового просмотра. Это относится и к удалению по UUID, массовому удалению, пакетным изменениям и удалениям, очистке бинарного поля. Само `confirm: true` без подходящего токена не разрешает выполнение.

Если платформа предоставляет ETag, `expected_etag` позволяет проверить версию и передать `If-Match`. Если ETag отсутствует, сервер возвращает `concurrency_unsupported` до записи. Проверка состояния перед выполнением не заменяет атомарный контроль версии на платформе: при отсутствии поддержки ETag остаётся короткий промежуток между проверкой и изменением.

### Готовые карточки и аналитика

Ответы чтения содержат исходные поля и отдельное представление `display_records`/`field_labels`: русские подписи, названия связанных записей и даты в UTC. Сервер получает названия справочных записей группами; модель не должна вручную соединять UUID с названиями. Если связанные данные недоступны по правам, исходные UUID сохраняются и появляется предупреждение. По умолчанию выбирается компактный набор полезных полей; явный `select` задаёт нужные поля.

`bpm_aggregate_records` считает и группирует на стороне MCP-сервера:

```json
{
  "collection": "Opportunity",
  "group_by": ["Stage"],
  "metrics": [
    { "field": "Amount", "op": "sum", "alias": "total_amount" },
    { "field": "Amount", "op": "avg", "alias": "average_amount" }
  ],
  "max_records": 5000
}
```

Поддержаны `sum`, `avg`, `min`, `max`; количество записей есть в каждой группе. Числа возвращаются десятичными строками, сумма не теряет точность из-за двоичной арифметики, среднее округляется до 6 знаков. В ответе есть число обработанных записей и `complete`: если анализ достиг лимита, показатели относятся только к прочитанной выборке. По умолчанию анализируется до 5000 записей, максимально — 20 000; выдача групп тоже ограничена.

`bpm_find_duplicates` принимает `fields`, например `["Email"]` или `["Name", "City"]`. Сервер нормализует ключи и возвращает группы кандидатов с UUID и примерами. Пустые ключи не объединяются. Совпадение не доказывает, что записи описывают одного человека или компанию; автоматического объединения и удаления нет. `complete=false` явно означает частичную проверку.

Без `fields` этот инструмент использует профили сравнения email, телефона, ИНН и имени, оценивает кандидатов и рекомендует основную запись. `bpm_check_duplicates` проверяет конкретную запись, а `bpm_merge_duplicates` выполняет отдельный сценарий объединения с предварительным просмотром.

`bpm_record_card` собирает карточку с её связями; `bpm_get_relations` описывает доступные связи. `bpm_whoami` возвращает текущего пользователя и его часовой пояс, `bpm_my_agenda` собирает его повестку. `bpm_aggregate` группирует прочитанные записи на стороне MCP-сервера, поддерживает календарные интервалы и сравнение периодов. Его числовые показатели используют JavaScript Number; для точных сумм Decimal и больших Int64 используйте `bpm_aggregate_records`.

## Инструменты

Полные входные и выходные схемы доступны через MCP `tools/list`; они являются контрактом текущей сборки.

При включённом журнале дополнительно доступен `bpm_get_operation`; `bpm_init` появляется только при отдельном разрешении env-creds.

| Бизнес-процессы               | `bpm_run_process`, `bpm_exec_process_element`                                                                                                         |
| Локальная авторизация, opt-in | `bpm_init`                                                                                                                                            |

`bpm_get_enum_values` возвращает значения целевого справочника, признак полноты и продолжение. Кэши справочных значений разделены по сессии и подключению. Для больших справочников используйте страницы; отсутствие записи в неполной странице не означает отсутствие значения в справочнике.

Пакетные ответы сопоставляются по ID подзапросов. Для каждой операции сохраняется результат; пропущенные и неизвестные исходы отличаются от ошибок. `$batch` не является гарантированной транзакцией: уже выполненные операции не откатываются автоматически. При `continue_on_error=false` следующие порции после ошибки не отправляются; после неопределённого исхода дальнейшая отправка также прекращается.

При недоступности нативного `$batch`, включая OData v3, сервер выполняет операции последовательно и сообщает выбранный режим. Decimal/Int64 сохраняют точность: в нативном batch числовые токены формируются только для полей, подтверждённых метаданными.

Сценарии проверяют переданные владельца, связи и значения до записи. Ошибка после частичного выполнения содержит выполненные шаги и известные UUID, чтобы можно было продолжить или исправить состояние без повторного создания.

Prompts: `getting_started`, `quick_search`, `create_contact_flow`, `weekly_report`, `cleanup_duplicates_check`, `pipeline_analysis`. Схемы и справочники также доступны через MCP resources.

## Ошибки и безопасный повтор

Ошибки содержат стабильный `code`, пояснение и `next_steps`.

| Код                       | Действие                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `lookup_ambiguous`        | Выбрать точную запись из кандидатов; изменение ещё не выполнено                                 |
| `validation`              | Исправить тип, поле или значение                                                                |
| `auth_required`           | Обновить сессию пользователя                                                                    |
| `concurrency_conflict`    | Прочитать актуальную запись и пересмотреть изменение                                            |
| `concurrency_unsupported` | Платформа не предоставляет требуемую защиту ETag                                                |
| `idempotency_conflict`    | Ключ уже соответствует записи с другими значениями; проверить намерение                         |
| `outcome_unknown`         | Проверить состояние: изменение могло выполниться; `safe_to_retry=false` запрещает слепой повтор |

Чтение может повторяться при временных 5xx/429 с учётом `Retry-After`. Изменения, загрузка файлов, `$batch` и запускающий процесс GET после 5xx, потери соединения или таймаута автоматически не повторяются. Истечение сессии допускает один повтор после определённого отказа авторизации. Таймаут HTTP-запроса охватывает попытки чтения и задержки между ними.

## Docker

Образ работает под пользователем `node`, слушает `0.0.0.0:8007` внутри контейнера и требует явного Host allowlist.

Начальный профиль запуска ниже сохраняет **1 vCPU и 512 MiB RAM**. Вместимость для реальной нагрузки нужно измерять на целевых запросах: локальный тест параллельности не устанавливает производственную пропускную способность.

```bash
docker build -t mcp-bpmsoft .
docker run --rm --name mcp-bpmsoft \
  --cpus=1 --memory=512m --memory-swap=512m \
  -p 127.0.0.1:8007:8007 \
  -e BPMSOFT_URL=https://bpm.example.ru \
  -e MCP_ALLOWED_HOSTS=127.0.0.1:8007,localhost:8007,mcp.example.ru \
  mcp-bpmsoft
```

При работе через `file_path` или `save_path` относительные HTTP-пути относятся к личному каталогу `BPMSOFT_FILE_ROOT/<tenant-hash>/<user-hash>`. Хэш стенда включает настроенный ID и нормализованный URL; хэш пользователя строится из UUID, подтверждённого BPMSoft. Cookies и входящий пользовательский ID не определяют имя каталога. Смена сессии того же пользователя сохраняет его файлы; другой стенд или пользователь не получают доступ к ним. Каталоги имеют права `0700`, новые файлы — `0600`; ссылки и выход за личный каталог запрещены, существующие файлы не перезаписываются.

Оператор заранее создаёт корень обмена и предоставляет процессу права записи. Для контейнера нужен отдельный том, доступный пользователю `node` (UID/GID 1000); для журнала — второй постоянный том. Старые HTTP-файлы в общем корне автоматически не становятся личными: перенос выполняется оператором после подтверждения владельца и стенда, без копирования данных всем пользователям. Локальный доверенный stdio сохраняет прежние пути. Альтернатива — `content_base64` и `return_base64`; учитывайте также HTTP-лимит тела запроса 4 МиБ.

Для HTTPS reverse proxy используйте его реальный внешний Host в allowlist. Не помещайте учётные данные в образ. Dev-образ собирается через `Dockerfile.dev`; изменения исходников пересобираются и перезапускают сервер.

## Проверка и эксплуатация

```bash
npm run build
npm run lint
npm test
npm run format:check
```

CI запускает эти проверки на Node.js 22 и 24. Интеграционные тесты HTTP слушают только локальный интерфейс и не требуют настоящего BPMSoft или реальных секретов.

`BPMSOFT_DEBUG=1` показывает метод, путь и статус; query string в журнал не записывается. `trace` также пишет тела запросов и ответов, маскируя известные секретные поля и заголовки. Данные CRM в телах остаются видимыми: trace используйте только при контролируемой отладке.

Поддерживаются OData v4 (`/odata` для .NET 8, `/0/odata` для .NET Framework) и v3 (`/0/ServiceModel/EntityDataService.svc`). Нативный `$batch` на v3 не поддерживается; пакетные инструменты MCP выполняют операции последовательно. Наличие конкретной коллекции, бизнес-процесса, русских подписей и платформенных правил зависит от инстанса и прав пользователя.
